# E2E を流すタイミング（TEST-05）の根拠

2026-10-27 に、E2E を「main へのマージ時」から「main に入る前の必須チェック」に移したときの記録（#52）。

## マージ後に流す形をやめた理由

マージ後に流すと、E2E が落ちたときには変更がもう main に入っている。main が赤いまま次の変更が積まれ、戻すか直すまで全員がその上で作業することになる。必須チェックにすれば、main は常に E2E を通った状態になる。

## 採らなかった案

| 案                                                        | 採らなかった理由                                                                                                                                                                                                                                                                                |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| develop ブランチで統合し、develop → main の PR でだけ E2E | 統合が遅れ、E2E が多くの変更をまとめて落とすので原因を絞りにくい。develop → main の PR は squash できない（WF-04）、issue と「計画との差異」の扱い（WF-01・05）、自動削除の除外（WF-06）など、規約に例外が増える。Git Flow が合うのは、版を分けて保守する製品やリリースをまとめる必要があるとき |
| merge queue（`merge_group`）でマージ直前に1回だけ流す     | push のたびに流さずに済む最も素直な形だが、個人アカウントのリポジトリでは使えない（2026-10 時点で dev-standards は個人アカウント）。Organization に移したら、まずこれに切り替える                                                                                                               |
| 変更したファイルに関係する E2E だけ流す                   | 共有部品の変更による回帰を取りこぼす。関係を正しく辿る仕組み（依存グラフやカバレッジの対応付け）を保つ費用も大きい。関門にはしない（ローカルで関係する spec だけ流すのは構わない）                                                                                                              |

## 遅くなったときの逃がし方

E2E は主要フローのハッピーパスに絞り、PR で全件を流しても数分で終わる規模を保つのが前提。それでも遅くなったら、次の順に逃がす。

1. **並列化（shard）**: 全件のまま速くする。保証する範囲は変わらない
2. **smoke と全件に分ける**: `@smoke` のタグを付けたものだけを PR の必須チェックにし、全件は main に対して夜間（schedule）に流す。夜間に落ちたら issue を自動で立て、main の回帰として直す

2 は main に入る前の保証が smoke の範囲に狭まるので、1 で足りないときだけ使う。
