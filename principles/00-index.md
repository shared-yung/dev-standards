# 開発原則（言語・フレームワーク非依存）

全プロジェクト共通の前提。プロジェクト固有の事情はプロジェクト側の CLAUDE.md が優先する。実体は dev-standards リポジトリ（ここは配布されたコピー。直接編集しない）。

- `principles/`（常に読み込む）: 何を・なぜ。手段は書かない
- `stacks/<スタック>/`（そのスタックのファイルを触ったときだけ読み込む）: どうやって。各原則の実装・対象外・逸脱を対応表で示す
- **計画・設計の段階では `stacks/` がまだ読み込まれていない。着手前に `~/.claude/rules/dev-standards/stacks/<スタック>/00-index.md` を Read で開く**
- 未登録のスタックでは、下の「適合性の確認」で各原則を判断し、結果をプロジェクトの ADR に残す

## 読み方

- 見出しは `ID 名前〔階層〕`。〔必須〕は実験でも外さない（安全と記録）。〔標準〕は Trial を宣言したプロジェクトで、宣言したものだけ置き換えてよい
- 強制の優先順位: 言語の仕組み（コンパイラ・型・可視性・パッケージ境界）＞ 静的解析 ＞ テスト ＞ フック・レビュー

## 適合性の確認

この原則の多くは TypeScript / Vue での実践から抽出したもので、**言語やフレームワークによっては不適切、またはより良い手段がありうる**。具体化するときは原則ごとに確かめ、スタックの対応表に書く。

1. 言語の仕組みで同じ目的をより強く・自然に達成できるなら、そちらを採る
2. 言語の慣習と衝突するなら目的に立ち返り、目的を損なわない限り慣習を優先する
3. 目的がその言語・規模で成り立たないなら「対象外」とし、理由を書く
4. 原則の書き方が特定の言語に寄っていると分かったら、原則のほうを直す

逸脱は禁止ではない。記録が無いことが問題。

## 標準と実験（Technology Radar）

既定は Adopt（この原則とスタック）。新しい手法は新規・短期・小規模のプロジェクトで Trial として試す。プロジェクトの CLAUDE.md に `Trial: <手法>（置き換える原則: <ID>）` と書き、1プロジェクトで同時に1〜2個まで。観察は dev-standards の `experiments/` に追記し、振り返りで Adopt／Trial 継続／Hold を決める（手順は `radar/README.md`）。
