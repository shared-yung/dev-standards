# 原則への適合の監査

仕組み（hook・CI・テンプレート・ガードレール）のずれは `sync-repo --check` で、コードの構成（原則への適合）は対応表で調べる。**監査はコードを変えない。** 直すのは、監査で立てた issue を起点にした別の作業。

このスキルの実体は dev-standards リポジトリの `skills/standards-audit/`。`~/.claude/skills/` にあるのは `bun run install-rules` が配ったコピーなので、直接編集しない。以下の `bun run` は dev-standards のクローン（場所は `~/.claude/CLAUDE.md`）で実行する。

## 1. 対象とスタックを決める

- スタックは対象の `.dev-standards.json` の `stack`。無ければ構成（`package.json` / `pyproject.toml` など）から推測し、ユーザーに確かめる
- モノレポ（REPO-04）では、ルートの1階層下のプロジェクトごとにスタックを決めて監査する
- 対象の作業ツリーに未コミットの変更が無いことを `git status` で確かめる（手順 3 で置いたファイルを確実に消すため）

## 2. 仕組みのずれを見る

```bash
bun run sync-repo <対象のパス> --check                    # 記録があるとき
bun run sync-repo <対象のパス> --check --stack <スタック>  # 記録が無いとき
```

ずれは原則ごとに見るのではなく、まとめて1件の不足にする（直す手段は `sync-repo` を流すことで同じ）。

## 3. 対応表を1行ずつ判定する

`~/.claude/rules/dev-standards/stacks/<スタック>/00-index.md` の「原則との対応」を上から順に見る。`WF-*` のように別のスタックを指す行は、指す先の対応表の行に展開する。

| 判定             | 条件                                                                        |
| ---------------- | --------------------------------------------------------------------------- |
| 満たす           | 手段が置かれ、効いていることを確かめた                                      |
| 不足             | 手段が無い、または置かれているが効いていない                                |
| 逸脱が未記録     | 手段と違うやり方をしているのに、対応表にもプロジェクトの ADR にも理由が無い |
| 対象外（妥当）   | 対応表の「対象外」「逸脱」の理由が、このリポジトリの事情に合っている        |
| 対象外（要確認） | 理由がこのリポジトリには当てはまらない（例: UI が無い前提なのに UI がある） |

根拠は次のどれかで示し、表に書く。推測だけで「満たす」にしない。

- **設定ファイル**: 該当の設定の `file:line`
- **意図的な違反**: 違反するファイルを置き、lint・型検査・テストが期待した理由で落ちるかを見る。置いたファイルはその場で消し、最後に `git status` が空であることを確かめる。強制の手段（ARCH-03・CODE-02・CODE-06・I18N-01 など）は設定があるだけでは「満たす」にしない
- **docs の有無**: `docs/{spec,architecture,adr}/` や ADR の該当箇所

対応表の「対象外」「逸脱」の行は、理由がリポジトリの事情に合っているかだけを見る。手段の良し悪しは監査しない（それは dev-standards の issue にする）。対応表に「未検証」とある行は、確かめた結果を報告に分けて書く（dev-standards の対応表を更新する材料になる）。

## 4. 結果を示し、issue 案を作る

結果は1つの表にする。

| ID  | 判定 | 根拠 |
| --- | ---- | ---- |

続けて、不足と「逸脱が未記録」「対象外（要確認）」ごとに issue 案を作る。同じ手段で直るものは1件にまとめる。

- タイトル（対象リポジトリのコミット規約に従う。例 `feat(<scope>): ...`）
- 目的（どの原則の、何が足りないか）
- やること
- 完了条件（直ったことをどう確かめるか。手順 3 の根拠と同じやり方で）

## 5. issue を立てる

GR-04 のとおり、立てる issue を一覧にして示し、1回の承認でまとめて `gh issue create` する。一覧に無いものは立てない。立てるかどうか自体をユーザーが決めてよい（案を示すところで止める）。
