# 原則への適合の監査

仕組み（hook・CI・テンプレート・ガードレール）のずれは `sync-repo --check` で、コードの構成（原則への適合）は対応表で調べる。**監査はコードを変えない。** 直すのは、監査で立てた issue を起点にした別の作業。

このスキルの実体は dev-standards リポジトリの `skills/standards-audit/`。`~/.claude/skills/` にあるのは `bun run install-rules` が配ったコピーなので、直接編集しない。以下の `bun run` は dev-standards のクローン（場所は `~/.claude/CLAUDE.md`。その worktree でもよい）で実行する。

## 1. 準備

- **スタック**: 対象の `.dev-standards.json` の `stack`。無ければ構成（`package.json` / `pyproject.toml` など）から推測してユーザーに確かめる。確かめられない（subagent で動いている）ときは、推測したことを報告に書く
- **モノレポ**（REPO-04）: ルート（hook・CI・docs・ガードレール）は `github-workflow` と `claude-code` の対応表で、ルートの1階層下のプロジェクトはそれぞれの言語のスタックで見る。`packages/` の共有パッケージは、使う側のプロジェクトと同じスタックで見る
- **作業ツリー**: 未コミットの変更が無いことを `git status --porcelain` で確かめる（手順 3 で置いたファイルを確実に消すため）。あれば意図的な違反は行わず、そう報告する
- **ベースライン**: プロジェクトごとに lint・型検査・テストが今の状態で通るかを見る。依存が入っていなくて動かないときは、lockfile どおりに入れる（`bun install --frozen-lockfile`・`uv sync --locked`。変わるのは無視設定の対象だけ）。もとから落ちるものは、その旨を報告に書く

## 2. 仕組みのずれを見る

```bash
bun run sync-repo <対象のパス> --check                    # 記録があるとき
bun run sync-repo <対象のパス> --check --stack <スタック>  # 記録が無いとき
```

- 記録（`.dev-standards.json`）が無いと、置いてある管理ファイルはすべて「衝突（初回）」になる。対象のファイルと上流（`bundles/` の内容）を比べ、内容の違うものだけを報告に書く
- ずれは**まとめて1件の issue 案**にする（直す手段は `sync-repo` を流すことで同じ）。手順 3 では、手段が配られるファイルである行（例 WF-01 の commitlint、REPO-01 の `.gitattributes`）を、このずれを根拠に「不足」にする

## 3. 対応表を1行ずつ判定する

言語のスタックの `~/.claude/rules/dev-standards/stacks/<スタック>/00-index.md` の「原則との対応」を上から順に見る。`WF-*` のように別のスタックを指す行は、指す先の対応表の行に展開する。同じ ID が複数の表にあるときは、言語のスタックの行を本体にする（指す先の表の「言語のスタックで扱う」は見ない）。判定と件数は、展開した ID ごとに1つ。1つの ID に複数の判定が当てはまるときは、下の表で上にあるほうを採る。

| 判定             | 条件                                                                                                      |
| ---------------- | --------------------------------------------------------------------------------------------------------- |
| 不足             | 手段が無い、または置かれているが効いていない                                                              |
| 逸脱が未記録     | 手段と違うやり方をしているのに、対応表にもプロジェクトの ADR にも理由が無い                               |
| 対象外（要確認） | 対応表の「対象外」「逸脱」の理由が、このリポジトリには当てはまらない（例: UI が無い前提なのに UI がある） |
| 該当なし         | 原則が前提にするコードがまだ無い（例: 外部 API と通信していないときの ARCH-05）。前提が何かを書く         |
| 対象外（妥当）   | 対応表の「対象外」「逸脱」の理由が、このリポジトリの事情に合っている                                      |
| 満たす           | 手段が置かれ、効いていることを確かめた                                                                    |

根拠は次のどれかで示し、表に書く。推測だけで「満たす」にしない。

- **設定ファイル**: 該当の設定の `file:line`
- **リモートの設定**: `gh api` の読み取り（GET）で見たリポジトリ設定・ruleset。読み取りは承認不要（GR-01）。書き込みはしない
- **意図的な違反**: 強制の手段（ARCH-03・CODE-02・CODE-06・I18N-01 など）は、設定があるだけでは「満たす」にしない。違反を置いて、期待した規則（ルール名・契約名）で落ちるかを見る
  - **新しいファイルだけで試す**（既存のファイルを書き換えない）。名前に `zz-audit-` を付け、プロジェクトのディレクトリで、そのプロジェクトのコマンド（`bun run lint` / `uv run ruff check` など）を対象のファイルに対して流す
  - git で追跡しているファイルだけを見る検査（python の `scripts/check-suppressions.ts` など）は、置いたファイルを `git add -N <ファイル>` で追跡に入れてから流す。未追跡のままだと違反が見えずに通る。消す前に `git rm -q --cached <ファイル>` で外す
  - 期待した規則以外の指摘（import の並びなど）は判定に使わない
  - 置いたファイルはその場で消し、最後に `git status --porcelain` が空であることを確かめて報告に書く。途中で止まったときも、次に始めるときにまず `zz-audit-` のファイルが残っていないかを見る
- **docs**: `docs/{spec,architecture,adr}/` や ADR の該当箇所。手段が規約（例 GR-04）の行は、AI 向け指示ファイルか docs に書かれているかで判定する
- 運用でしか確かめられない行（例 TEST-01 のテストを先に書く順序）は、判定を「満たす」にせず、根拠の欄に「運用は未検証」と書く

次のものは、対象のリポジトリではなく dev-standards の問題として報告に分けて書く（dev-standards に issue を立てる材料）。

- 手段の良し悪し（「対象外」「逸脱」の行は、理由がリポジトリの事情に合っているかだけを見る）
- 対応表の手段では原則を強制できない（例: 抑制の理由を検査する規則が無い、`null` の比較は落ちるが型には残る）
- 対応表に「未検証」とある行で、確かめた結果

## 4. 結果を示し、issue 案を作る

結果は1つの表にする。強制の欄は、機械で落ちる（`機械`）か、規約・人の注意に頼る（`規約`）か。

| ID  | 判定 | 強制 | 根拠 |
| --- | ---- | ---- | ---- |

続けて判定ごとの件数、dev-standards の問題を書き、不足と「逸脱が未記録」「対象外（要確認）」ごとに issue 案を作る。同じ手段で直るものは1件にまとめる。本文は対象のリポジトリの issue テンプレート（`.github/ISSUE_TEMPLATE/`）に合わせ、無ければ次の形にする。

- タイトル（対象リポジトリのコミット規約に従う。例 `feat(<scope>): ...`）
- 目的（どの原則の、何が足りないか）
- やること
- 完了条件（直ったことをどう確かめるか。手順 3 の根拠と同じやり方で）

## 5. issue を立てる

GR-04 のとおり、立てる issue を一覧にして示し、1回の承認でまとめて `gh issue create` する。一覧に無いものは立てない。立てるかどうか自体をユーザーが決めてよい（案を示すところで止める）。
