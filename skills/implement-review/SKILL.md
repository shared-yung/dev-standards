# 実装とレビューの分業

原則は AGENT-01〜04（`~/.claude/rules/dev-standards/principles/agent.md`）、手段の一覧は `stacks/claude-code/00-index.md`。ここには手順だけを書く。

## 1. 調査（必要なときだけ）

- 読むファイルが多い調査は `Explore` subagent に任せ、要約だけを受け取る。何を調べて何を返してほしいかを具体的に書く
- 変更が1文で言えるほど小さいなら、調査も計画も省く

## 2. 実装

- メインのセッションで実装する。テストと検査（型・lint・テスト）を通してからレビューに回す。**機械で落ちるものをレビュアーに見つけさせない**
- 並列の subagent やチームに実装を分けない。並列にするのは、互いに依存せず触るファイルも重ならないタスクだけ

## 3. レビュー（1回目）

`reviewer` subagent を呼ぶ。渡すのは次の3つだけで、実装の経緯や迷ったことは渡さない（新しい文脈で評価させるため）。

- 差分の範囲（例: `git diff main...HEAD`）
- issue の計画（`gh issue view <番号>` の本文、または計画ファイル）
- 「1回目のレビュー」であること

## 4. 修正

- 「要修正」を直す。直したら検査を通し直す
- 「nit」は直さなくてよい。直すなら1コミットにまとめる
- 「判断事項」は直さずに残す（6 で示す）

## 5. レビュー（2回目）

`reviewer` を新しく呼び直す（前の呼び出しを続けない）。渡すのは更新した差分・計画・前回の「要修正」・「2回目のレビュー」であること。

**2回目で終わり。** 3回目のレビューはしない。

## 6. 判断事項の提示

2回目のレビューで残ったもの（直っていない「要修正」、新しい指摘、すべての「判断事項」）を、ユーザーへの質問として示して止まる。

- 1件ごとに論点・選択肢・推奨を書く
- 決まったことは PR 本文の「計画との差異」に書く（WF-05）

## 費用の目安

- レビュアーが読むのは diff と計画だけなので、増えるトークンは diff の大きさにほぼ比例する。大きな PR では、レビューの前に PR を分けられないかを先に考える
- 調査やレビューの subagent が使ったトークンも使用量に数えられる。`/usage` の attribution で割合を見る
