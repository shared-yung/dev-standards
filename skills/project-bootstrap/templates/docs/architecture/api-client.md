# API クライアントと型生成

バックエンドは **ASP.NET**。バックエンド側で OpenAPI の yaml を生成し、フロントはそこから型を自動生成する。

## 構成

- 型生成: `openapi-typescript`
- HTTP クライアント: `openapi-fetch`（生成された型をそのまま使える軽量クライアント）
- 置き場所: workspace パッケージ `packages/api-client/`

複数プロジェクトから同じ API を叩く前提なので、生成物はプロジェクト内ではなく共有パッケージに置く。

## 最重要の制約

**生成された型を import してよいのは `infrastructure` 層だけ。**

infrastructure で API のレスポンスを受け取り、そこで domain の型へマッピングする（腐敗防止層）。API レスポンスの型がそのまま use-case や画面に現れていたら、マッピングが抜けているサイン。

この制約がないと、バックエンドのスキーマ変更が domain に直撃してオニオンの依存方向が壊れる。フロントとバックエンドのリリースサイクルが分かれている以上、境界にクッションを置く必要がある。

## 生成物の扱い

- 生成コードは**リポジトリにコミットする**（型が無いと IDE もビルドも動かないため）
- CI で再生成して差分が出たら fail させ、yaml とのドリフトを検出する
- Prettier / ESLint の対象からは除外する（`.prettierignore` に登録済み）

## zod との使い分け

生成された型は「形」の情報だけで、実行時の検証はしない。**実行時検証が必要な境界だけ zod スキーマを手書き**し、そこで domain の型に変換する。全エンドポイントに zod を二重定義すると生成のメリットが消えるので、外部入力の信頼度で使い分ける。

zod は domain 層で唯一 import を許可している外部ライブラリなので、変換後の型を domain 側に置くのは問題ない。
