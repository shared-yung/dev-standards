# issue-driven 開発

**すべての変更は GitHub Issue から始める。** issue のない変更は入れない。例外は最初のコミット（root commit）だけ。

## 手順

1. Issue を立てる（機能追加なら「機能追加・変更」テンプレート、バグなら「バグ報告」）
2. issue 番号を使ってブランチを切る — `feat/42-quiz-scoring`
3. コミットのフッターに `Refs: #42` を書く
4. PR を出し、本文に `Closes #42` を書く
5. PR 本文の「計画との差異」節を埋める（ずれが無ければ「なし」）
6. CI が通ったら **人間が** squash merge する（AI エージェントは実行しない）

## なぜ3層で強制するのか

git hook だけでは `git commit --no-verify` や `git push --no-verify` で迂回できる。ルールを実効的にしているのは CI とブランチ保護の側で、hook は「早く気づくため」の仕組みという位置づけ。

| 層                   | 何を見るか                                                                  | 迂回 |
| -------------------- | --------------------------------------------------------------------------- | ---- |
| lefthook（ローカル） | コミットメッセージ、staged ファイルの lint、push 時のブランチ名             | 可能 |
| GitHub Actions       | 全コミット、ブランチ名、PR タイトル、issue リンクの有無、計画との差異の記入 | 不可 |
| ブランチ保護         | main への直 push 禁止、PR 必須、上記チェックの通過必須                      | 不可 |

「コミットメッセージだけ形式を整えて issue を立てない」という抜け道は、`Conventions` ワークフローの **PR に issue がリンクされているか検証** ステップが塞ぐ。これは GraphQL の `closingIssuesReferences` を見ているので、本文に `Closes #<番号>` を書いて実際に issue と紐づいていないと通らない。

## マージは人間が行う

**マージは AI エージェントに実行させない。** `gh pr merge` は `.claude/settings.json` の `deny` に入れてあり、承認しようとしても実行できない。

理由は、承認プロンプトが「このコマンドを実行してよいか」を聞くだけで**差分を表示しない**こと。マージの是非は差分と CI を見て判断するものなので、GitHub の UI で確認しながら決める。プロンプトでの承認は権限チェックであって、レビューの代わりにはならない。

AI エージェントが行うのは PR の作成と CI 結果の報告まで。マージ後の同期は指示を受けてから行う。

## 計画との差異を issue に残す

issue は**着手前の計画**で書かれる。実装中に判明した制約で方針が変わっても issue 側には反映されないため、放っておくとクローズされた issue が事実と食い違う記録になる。

**目的は差異をなくすことではない。** 実装中に計画が変わるのは正常で、むしろ調査が効いた証拠であることも多い。問題は変わった事実と経緯が残らないこと。

### 仕組み

1. PR テンプレートに `## 計画との差異` 節がある
2. `Conventions` ワークフローが、この節が空でないことを検証する（`scripts/check-pr-divergence.mjs`）。ずれが無い場合は「なし」とだけ書けば通る
3. マージ時に `PR Merged` ワークフローがこの節を抽出し、`Closes` でリンクされた issue へコメントとして投稿する

3 によって、**クローズされた issue 単体を読めば実態が分かる**状態になる。PR を辿る必要がない。

### 書く内容

計画とずれた点と、**なぜずれたか**。判断の理由が本体で、変更点の列挙だけでは後から役に立たない。

> 計画では `tsconfig.json` を `../tsconfig.base.json` の extends に差し替える想定だったが、Quasar の型サポートには `./.quasar/tsconfig.json` が必須だったため、配列 extends で両方を適用する形にした。

### 制約

fork からの PR では `pull_request` の closed イベントのトークンが読み取り専用になり、コメントを投稿できない。所有者のみが push する前提で運用している。

## 最初のコミットの例外

`scripts/commit-msg.sh` が `git rev-parse -q --verify HEAD` で親コミットの有無を判定し、root commit なら commitlint を実行しない。

CI 側は PR の base..head 範囲しか検証しないため、root commit がチェック対象に入ることはない。初回コミットは main に直接置き、その後 `scripts/setup-branch-protection.sh` を実行してブランチ保護を有効化する。
