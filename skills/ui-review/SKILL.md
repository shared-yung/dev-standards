# UI のレビュー

原則は UI-01〜04（`~/.claude/rules/dev-standards/principles/ui.md`）、Quasar での手段は `stacks/typescript-vue/ui.md`。ここには手順だけを書く。

このスキルの実体は dev-standards リポジトリの `skills/ui-review/`。`~/.claude/skills/` にあるのは `bun run install-rules` が配ったコピーなので、直接編集しない。

**実装したのとは別の文脈で使う**（UI-04・AGENT-01）。実装したセッションで使うときは、subagent に手順ごと任せ、渡すのは差分の範囲・issue の計画・`DESIGN.md` の場所だけにする。

## 1. 準備

- 対象のプロジェクトの `DESIGN.md` を読む。無い、または空欄が多いときは、それ自体を「要修正」に書く（見た目の判断の基準が無い）
- レビューする範囲（`git diff main...HEAD -- '*.vue' '*.scss'` など）と、変わった画面（ルート）を一覧にする

## 2. コードを見る

変わったファイルを [references/web-interface-guidelines.md](references/web-interface-guidelines.md) の観点で見る。

- lint・型検査・テストで落ちるもの（`vue/no-static-inline-styles`・`no-raw-text` など）は指摘しない（AGENT-02）
- `DESIGN.md` に無い色・余白・文字の大きさを使っていないか（`<style>` の中の直書きは機械で落ちない）
- データを読む画面に、空・読み込み・エラーの3つがあるか（UI-01）

## 3. 描画して見る

1. dev サーバーを起動する（`.claude/launch.json` の設定。Claude Code のデスクトップ版なら `preview_start`）
2. 変わった画面を、幅 375・768・1280 で開いてスクリーンショットを撮る
3. 空・読み込み・エラーの状態を出して撮る。出せない状態は、出し方が無いこと自体を報告に書く（テストか開発用の切り替えが要る）
4. キーボードだけで主要な操作を最後まで行い、フォーカスが見えることを確かめる（UI-02）
5. ダークのテーマを持つなら、ダークでも 2 を撮る

スクリーンショットで見ること:

- 幅ごとに、はみ出し・重なり・不要なスクロールバーが無いか
- 見出し・本文・補足の違いが一目で分かるか。主要な操作が1つに絞れているか
- 余白が `DESIGN.md` の段階に沿っていて、関係の近いものが近くにあるか
- 実際の長さの文言・件数・桁数で崩れないか（仮の短い文言で済ませていないか）

## 4. 報告する

ファイルごと・画面ごとにまとめ、`file:line` か「画面・幅・状態」で場所を示す。3つに分ける。

- **要修正**: UI-01〜04 と `DESIGN.md` に反するもの。根拠（原則の ID か `DESIGN.md` の節）を添える
- **判断事項**: `DESIGN.md` に決まりが無く、決める必要があるもの。選択肢を添える
- **センス**: 見た目の方向についての意見（`stacks/typescript-vue/ui.md` の「センス」）。直すかどうかはユーザーが決める。最大5件

撮ったスクリーンショットの幅と状態を一覧にし、PR 本文に貼れる形で最後に書く。
